# Phase 4 walk design and release procedure

Presented October 12, 2026, before migration implementation. Necessary migrations are authorized by the user; live application still requires a real database connection and the checks below.

## Model and behavior

`walks(id uuid, created_at timestamptz, user_name text, revision integer, provenance text, deleted_at timestamptz)` owns an outing. `created_at` is the occurrence time, preserving the existing API/calendar naming. `logs.walk_id` is a nullable FK during migration. Existing log UUIDs, timestamps, people, notes and outcomes survive backfill. New outcomes share their parent's time/person. No unique outcome constraint is imposed on historical rows: repeated outcomes must not be discarded.

Public reads fetch active parents with nested outcomes in one request, scoped by parent occurrence time. The existing shared store retains its freshness, sequencing and independent error rules. Walk counts, points, champions and mutation targets use parents. Bathroom totals, streaks and bathroom time distributions continue reading original date-scoped logs, including historical outcomes whose estimated parent lies in another day. Exact log reads still share the existing cache. Today starts seven independent reads rather than five, with no duplicate subscriptions or blocking on leaderboard/recent reads. The old grouping helper remains only for historical comparisons/tests. There is no fallback to guessed groups after a failed parent read.

Neither means no poop and no pee: a parent with zero outcome rows. It contributes one walk toward the five-walk daily goal, five points and one walk in the champion tiebreak. It contributes zero bathroom events and does not affect the three-poop goal/streak. Bathroom time-of-day distribution continues measuring bathroom events. Routines/reminder scoring, device-local calendar and Phase 1–3 interaction contracts stay unchanged.

POST `/api/walks`: `{requestId, createdAt, userName, poop, pee}`. PATCH adds `{walkId, expectedRevision}`; DELETE uses `{requestId, walkId, expectedRevision}`. Strict schemas reject the former arbitrary `logIds` contract. Each RPC is one transaction. Updates/deletions lock the parent and compare revisions; conflicting or removed targets return 409. Edits retain matching outcome rows/notes and remove/add only the changed outcome types. Removal soft-deletes the parent; public parent/log policies hide removed rows. Successful responses include the stable walk ID and revision.

Private request receipts retain operation, exact payload and result. A transaction advisory lock serializes a request UUID; repeating the same request returns its original result, including after deletion, and reusing it with different inputs is rejected. The client keeps one failed request per mounted mutation path and reuses its UUID/timestamp for an unchanged retry. Changing input starts a new request; canceling and reopening a creation form also starts a new draft identity even with identical input. The draft identity is client-only and is stripped before the API request. This is not persistent offline storage: reload or abandoning a draft can lose its retry UUID, so check history after an uncertain save across reload.

RLS permits public SELECT on active care records; anon/authenticated have no writes or mutation-function execution. Only service_role executes RPCs after the existing server PIN check. Fixed search paths/qualified objects prevent definer lookup surprises. Receipts, archived source and mapping are in a private schema, not exposed publicly.

## Historical preservation

Migration 001 is additive and installs versioned RPCs plus wrappers for old RPC signatures. It does not backfill. SQL preview groups only unlinked logs with the original adjacent-gap <=30-minute rule, ordering ties by UUID for determinism. Each candidate lists original IDs, latest time/person, mixed walkers, duplicate types, chains longer than 30 minutes and local-date/month crossings. Singleton parents are `legacy_single`; every multi-row group is `legacy_estimate` and is visibly labeled Historical estimate. This preserves the historical assumption rather than claiming recovered identity.

Preview includes per-day and per-month/person walk-count and point comparisons in the explicitly chosen migration timezone (America/New_York by default). The old client grouped separately within each query window. Groups crossing a calendar boundary can therefore change walk counts/points after parent scoping; all such deltas must be reviewed. Bathroom counts/goals/streaks keep their original outcome dates through separate shared reads. Device calendars remain local; equivalence of walk counts in every possible timezone cannot be guaranteed. Equal-time groups are flagged: UUID ordering supplies deterministic attribution for the preview/backfill, whereas the old timestamp-only query did not guarantee tied ordering. Preview comparisons use this deterministic tie rule and cannot establish the old display's arbitrary tied winner; review mixed-walker ties explicitly. Mixed original bathroom attribution remains on historical logs while walk points retain the group's chosen latest walker. No ambiguous group is silently split, no old bathroom rows are replaced, and no zero-outcome history is invented.

Save/export the preview before conversion. Backfill locks the source/parent tables against writes, requires the exact source fingerprint and selected timezone from the preview, archives every original row and links each to the chosen parent in a private mapping. A changed source aborts. Original data must compare equal except for the added walk_id. After backfill, verify all rows have parents; only then apply the separate NOT NULL constraint. No automatic heuristic rerun merges new walks.

## Release and recovery

1. Put writes in maintenance; export full logs/walks, activities/reminders, function definitions and grants. Retain the current app build and database backup. Verify the export can be read/restored on a disposable database.
2. Apply `migrations/001-explicit-walks.sql` (transactional additive schema/RPCs). Existing bathroom-only clients can still write using guarded wrappers; they cannot accurately display Neither. Maintenance is preferred throughout cutover.
3. Run `migrations/002-backfill-preview.sql` in the SQL editor. Export the full JSON result (groups and comparisons), resolve/review ambiguity and calendar deltas, and retain the fingerprint/timezone. The preservation default is explicitly historical estimates. If actual family knowledge warrants different grouping, do not use this default conversion until a reviewed mapping is prepared.
4. Invoke the private backfill with the reviewed fingerprint/timezone. Run `migrations/003-verify-and-constrain.sql`; it aborts on missing links, archive changes or mapping mismatches before making the FK mandatory. Refresh the PostgREST schema cache.
5. Release the coordinated parent reader/API/UI. Force old tabs to reload. Verify public/PIN access and real create/edit/delete/readback, including Neither and two simultaneous/nearby outings, before reopening writes.
6. Stop if counts, source integrity, permissions or persistence differ from the preview. Do not drop legacy functions, logs, private receipts or archives during this release.

Before application cutover, the private recovery function unlinks only untouched backfilled parents and removes their mapping/parents; it refuses edited/deleted legacy parents and the final NOT NULL constraint must first be dropped in a maintenance transaction. It retains the immutable archive and leaves all new walks untouched. Test this on a restored copy before live use. After new writes, prefer the corrected explicit reader with writes paused; restoring only the old app would omit Neither and resume inaccurate grouping. Full rollback uses the pre-release backup plus a reviewed export/replay of all subsequent parents/outcomes; never drop parents to make an old reader appear complete. Intentional edits/deletions need a human reconciliation if replaying.

## Evidence required

Regression suite: identity separation at same/nearby times and across people, Both and Neither, bathroom counts/goals/streak/points, parent-only edits/deletes, stale revision, unauthorized calls and durable duplicate requests. Execute SQL on disposable PostgreSQL with forward/backfill/verification/recovery paths and permission checks. Browser: mobile/desktop, stable primary action, Neither create/edit/remove, failed save and explicit retry, saved/read-failed state, history/analytics/leaderboard, public read-only. Run full tests, typecheck, lint, production build and diff checks. The embedded PGlite runtime verifies PostgreSQL behavior with sequential transactions; it does not prove simultaneous connections or PostgREST schema discovery. Before live reopening, run two concurrent requests with the same UUID and competing revisions, verify the schema-cache/nested read, inspect actual stored values and check both family devices. Fixture/browser and disposable SQL evidence does not establish live Supabase persistence or physical-device behavior.
